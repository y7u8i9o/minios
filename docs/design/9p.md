# Host folders through virtio-9p (V5 of the 0.6.0 release)

The host shares a folder with the guest through virtio-9p (device 9) and
the protocol 9P2000.L. The QEMU of macOS has no vhost-user-fs, so virtiofs
is not available there. The guest mounts a share with the filesystem type
`9p`.

## Transport

`kernel/drivers/virtio/virtio_9p.c` accepts the modern PCI device 0x1049
and the transitional device 0x1009 with modern capabilities. It requires
`VIRTIO_9P_F_MOUNT_TAG` and reads the mount tag from the configuration
space. A tag has at most 31 characters, the longest name of a devfs node,
and contains no slash. A second device with the same tag is refused.

The device has one request queue. `virtio_9p_request` sends a chain of two
descriptors: the message for the host and the buffer for the answer. The
index of the head descriptor identifies the request in the queue and is
also the 9P tag of the message, so the tags of the pending requests
differ. `Tversion` carries `NOTAG`. The completion marks the request done,
and each waiter checks its own request. Several threads therefore have
requests pending at once, up to 64 with a queue of 128 entries.

Each device appears as `/dev/9p/TAG` (mode 0444). The file reports the
tag, the number of requests and the most requests that were pending at
once:

    tag host
    requests 1934
    most_pending 4

## Protocol

`kernel/fs/9p/client.c` builds and parses the messages. A message is a
header of size, type and tag, followed by the fields of its type in
little endian order. The client sends `Tversion` with a message size of
64 KiB and accepts a smaller size of the server. It implements `Tattach`,
`Twalk`, `Tgetattr`, `Tsetattr`, `Tlopen`, `Tlcreate`, `Tread`,
`Twrite`, `Tclunk`, `Treaddir`, `Tmkdir`, `Tunlinkat`, `Trenameat`,
`Tsymlink`, `Tlink`, `Treadlink`, `Tstatfs` and `Tfsync`. `Tlink` serves
the link operation of the VFS. One `Tread` or `Twrite` carries at most
60 KiB, the message size without the header, rounded down to whole pages.
An error answer `Rlerror` contains a Linux errno value. minios uses the
same numbers. Values that minios lacks become `EIO`, `ESTALE` becomes
`ENOENT` and `EDQUOT` becomes `ENOSPC`. The QEMU of macOS translates the
errno values of macOS before it sends them.

Fids are numbers from 0 to 4095 in a bitmap of the client. A failed walk
does not create its new fid, and the client returns that fid to the
bitmap without `Tclunk`.

## Filesystem

`kernel/fs/9p/9p.c` connects the client to the VFS. The source of a mount
is the mount tag. The filesystem has no options. The mount attaches the
root fid as uid 0, and the inode number of each file is the path of its
qid. The server gives each file of the share a different path.

Each cached inode has a fid that a walk reached and that is not opened.
Each open file has a fid of its own: a clone of the fid of its inode,
opened with `Tlopen` in the access mode of the file. A directory is
opened for reading. The client stores no data. Reads and writes go to the
host at once, and every lookup reads the attributes again with
`Tgetattr`. Opening a file reads them as well, which gives `O_APPEND` and
`SEEK_END` the size of the host. A file that the host changes shows its
new attributes at the next lookup. Mappings of a file use the generic
page cache of `filemap.md`, which reads and writes through the open file,
so programs on a share run and files on a share can be mapped.

The VFS reads an inode through `read_inode` with its number alone. A
lookup therefore walks to the name, reads the attributes and adds the
fid and the attributes to the list `pending` before it calls
`inode_get`. `read_inode` takes the entry of its number. When the inode
was cached already, the lookup clunks its fid and copies the new
attributes into the cached inode. When another thread read the same inode
first, `free_inode` clunks the fid. The root fid belongs to the
superblock, and `read_inode` uses it for the root without an entry in the
list.

`create` clones the fid of the directory and turns the clone into the new
file with `Tlcreate`. The client then clunks the clone and looks the new
name up. `unlink` and `rmdir` look the name up first and refuse a
directory with `EISDIR` and a file with `ENOTDIR`, because macOS answers
`unlink` of a directory with `EPERM`. A removed name lowers the link count
of a cached inode. Every change of a directory reads its attributes
again. `chmod` and `chown` send `Tsetattr`. The host decides whether it
can store an owner, and its refusal reaches the caller. `sync` sends
`Tfsync` for each open file of the share, which asks the host to write
the file to its disk. minios has no `fsync` call.

The owner and the mode of a file come from the host. With the security
model `none`, which `tools/run.sh` and the boot tests use, QEMU accesses
the files with the rights of the user who runs it, and the guest sees the
uid and gid of the host.

## Mounting

`mount -t 9p TAG DIR` mounts a share (`mount(1)`). After `/etc/fstab`,
`fsinit` mounts every tag of `/dev/9p` at `/mnt/TAG` and creates the
directories. A mount point that is mounted already is skipped. A failure
is reported and does not change the exit status of `fsinit`, because no
share is required for the boot. `tools/run.sh --share DIR` gives the guest
the folder DIR with the tag `host`:

    -fsdev local,id=share0,path=DIR,security_model=none
    -device virtio-9p-pci,fsdev=share0,mount_tag=host

## Tests

A case with a `share` file gets the scratch folder
`build/tests/<case>/share` with the tag `host`. An executable `mkshare` of
the case fills the folder, and `post` finds it in `SHARE`.

- `9p` (`user/etc/tests/9p.sh`): the script mounts the share with
  `mount -t 9p`, reads a file and a file in a folder of the host, follows
  a symbolic link and lists the folder. It writes and appends to a file,
  changes its mode, makes a symbolic and a hard link, makes, renames and
  removes files and folders, requires `rm` and `rmdir` to refuse a folder
  that is not empty, writes 1 MiB and compares it, and truncates a file.
  Four `cmp` processes read the large file at once, and `/dev/9p/host`
  must report at least two pending requests at once. The script copies
  `memtouch` to the share and runs it from there, runs
  `mmapfiletest /mnt/host/maptest` for the mappings, calls `df` and
  `sync`, unmounts and mounts the share again and reads the written file.
  `post` checks every change on the host.
- `9p_automount` (`kernel/tests/test_9p.c`): the test starts init and
  waits for `/mnt/host/hello.txt`, which `mkshare` wrote. The file must
  contain the text of the host, and `fsinit` must report the mount.

Both cases pass on x86_64 and aarch64.
